# Maestro's engine holds; its edges are not release-ready

Maestro delivers the thing it promises hardest to deliver — a crash-recoverable, replay-by-sequence durable-execution core that the project's own 6-node chaos harness drove through **4,221 workflows across 8 runs with 0 durable-state invariant violations** — and that core would remove several hundred lines of state-table, timer, correlation and recovery code from any Spring Boot service that orchestrates multi-step business flows. The value is real but bounded: it fits a microservice running tens to low thousands of in-flight workflows on business-latency timers, not a fleet-scale Temporal replacement, and the four structural gaps that bound it (no lock fencing, activity arguments never stored, the ×1000 sequence-depth ceiling, no history compaction) are design choices, not bugs. What is not ready is everything around the core: the flagship sample's saga comment is wrong in code, nothing purges `maestro_workflow_event`, every engine release so far has required a stop-the-fleet upgrade, the test kit never exercises the replay path where the likeliest production bugs live, and the admin dashboard is Kafka-only, unauthenticated and payload-blind. Three premises supplied to the researchers were corrected by the evidence and this report reflects the corrections: the `ActivityExecutionException` wrapping is a deliberate, documented contract (not a defect); the weekly chaos soak was intermittently red (5 failures in 10 weekly runs, with passes interleaved), not continuously red; and a Temporal-style `workflow.version()` API exists and works. Scored out of 10: value 7, correctness 7, operations 4, ease of use 6, market position 3. The verdict for a first release is: the engine can ship as a credible pre-1.0, but only after the sample/doc defects are fixed, a retention story exists, and the Java 25 floor is either justified in writing or relaxed — because the market slot Maestro targets is already occupied by DBOS Transact Java 1.0 on JDK 17.

*Scope and sourcing: five independent research notes (engine correctness, operations readiness, developer experience, red-team costs, competitive landscape) read the repository at `main` `c01d498` on 2026-11-04 without building or running anything. File citations below are repo-relative `path:line` as recorded in the notes; web citations are URLs. Where a note marked a finding as inference rather than a direct read, this report says so.*

## The replay core earns its durability claim

The engine is a pure memoizer: each activity, side effect, sleep, await, fork and version marker consumes one or two `int` sequence slots, and on recovery the proxy looks up `(instance_id, seq)` and either replays the stored result or executes live and appends ([ActivityInvocationHandler.java:331-372](maestro-core/src/main/java/io/b2mash/maestro/core/engine/ActivityInvocationHandler.java)). What lifts this above a naive memo cache is that every replay read is now guarded twice before any side effect: `UnknownHistoryGuard.requireKnown` stands the run down on an event type this build cannot read, then `ReplayGuard.requireMatch` compares the stored event's type and step name with the step the code is about to perform and stands down as `NONDETERMINISTIC_HISTORY` on mismatch ([ActivityInvocationHandler.java:343-352](maestro-core/src/main/java/io/b2mash/maestro/core/engine/ActivityInvocationHandler.java); [ReplayGuard.java:71-78](maestro-core/src/main/java/io/b2mash/maestro/core/engine/ReplayGuard.java)). The `ReplayGuard` Javadoc is candid that before this guard "a renamed or reordered activity silently returned another step's payload" ([ReplayGuard.java:10-34](maestro-core/src/main/java/io/b2mash/maestro/core/engine/ReplayGuard.java)); the fix is pinned by `ReplayDriftStandDownTest` across renamed activities, side effects on fork slots, sleeps on occupied slots and parallel arity mismatches ([ReplayDriftStandDownTest.java:102-348](maestro-core/src/test/java/io/b2mash/maestro/core/engine/ReplayDriftStandDownTest.java)).

The most carefully engineered part of the codebase is the control-flow design. The three signals that mean "this local run must stop now but the workflow has not failed" — `ExecutorShutdownException`, `WorkflowTerminatedException`, `UnknownWorkflowHistoryException` — extend a sealed `MaestroControlFlowError extends Error` so that a workflow author's ordinary `catch (Exception)` cannot swallow them and record a routine deploy as a business failure ([MaestroControlFlowError.java:18-56](maestro-core/src/main/java/io/b2mash/maestro/core/exception/MaestroControlFlowError.java)). The engine-correctness note audited every `catch (Throwable)` collection point and reflective unwrap in `maestro-core/src/main` and **found no violating catch site**: the executor's catch chain, `parallel()` branch collection, `RetryExecutor`, the activity proxy's attempt unwrap and `ParkingLot` all check `Error` before `Exception` and rethrow control-flow errors first ([WorkflowExecutor.java:1980-2054, 2099-2109](maestro-core/src/main/java/io/b2mash/maestro/core/engine/WorkflowExecutor.java); [DefaultWorkflowOperations.java:795-838](maestro-core/src/main/java/io/b2mash/maestro/core/engine/DefaultWorkflowOperations.java); [RetryExecutor.java:118-148](maestro-core/src/main/java/io/b2mash/maestro/core/retry/RetryExecutor.java)). Catch sites outside core (starter, admin, samples) were not audited.

Two premises the coordinator supplied turned out to be wrong, and both corrections favour the project. First, activity exceptions are *always* wrapped in `ActivityExecutionException`, live or on replay, and the sanctioned idiom is `causedBy(Class)` or `originalClassName()`; a replayed cause is a faithful reconstruction (the original type via a public `(String)` constructor, else `ReconstructedActivityFailure`) ([ActivityExecutionException.java:5-23, 61-92](maestro-core/src/main/java/io/b2mash/maestro/core/exception/ActivityExecutionException.java); [FailureReconstruction.java:61-83](maestro-core/src/main/java/io/b2mash/maestro/core/engine/FailureReconstruction.java)). This is a deliberate contract, honestly documented in `concepts.md:143-159` and used correctly by the payment sample; it is a Maestro-specific idiom every author must learn (the getting-started tutorial never shows it), but it is not a defect. Second, a real versioning API exists: `workflow.version(changeId, minSupported, maxSupported)` records `maxSupported` as a durable `VERSION_MARKER`, replays the recorded value forever, resolves pre-change histories to `DEFAULT_VERSION` *without consuming a slot* (so introducing a gate is safe for in-flight runs), and raises `UnsupportedWorkflowVersionException` when the floor is lifted past a recorded value ([WorkflowContext.java:600-690](maestro-core/src/main/java/io/b2mash/maestro/core/context/WorkflowContext.java); [DefaultWorkflowOperations.java:938-1090](maestro-core/src/main/java/io/b2mash/maestro/core/engine/DefaultWorkflowOperations.java); [concepts.md:509-546](docs/concepts.md)). It is Temporal's `getVersion` pattern, no more and no less.

Signals, timers and compensation all hold at the durability layer. A signal is written to the store before any wake and is consumed by `workflow_id` regardless of whether orphan adoption has run, so the three self-recovery cases (signal before `awaitSignal`, signal before start, signal while the service is down) are store-side guarantees ([SignalManager.java:348-400](maestro-core/src/main/java/io/b2mash/maestro/core/engine/SignalManager.java); [AbstractJdbcWorkflowStore.java:700](maestro-store-jdbc/src/main/java/io/b2mash/maestro/store/jdbc/AbstractJdbcWorkflowStore.java)). Timer firing is correct under dual leaders because the `PENDING→FIRED` CAS on the timer row is the arbiter and the poller never writes event-log rows; a "row fired, outcome not appended" crash self-heals on replay via `findTimer`, pinned by `EnginePostgresTimerIT` ([AbstractJdbcWorkflowStore.java:818-819](maestro-store-jdbc/src/main/java/io/b2mash/maestro/store/jdbc/AbstractJdbcWorkflowStore.java); [DefaultWorkflowOperations.java:307-345](maestro-core/src/main/java/io/b2mash/maestro/core/engine/DefaultWorkflowOperations.java)). Saga compensation is durable at step granularity, anchored in its own sequence block after the 2026-10-24 fix, replays without re-invoking completed steps, and never runs on control-flow errors; the full sequence layout `1,2001,3001,4001,4002000,...` is pinned against Postgres ([SagaManager.java:191-271, 377-393](maestro-core/src/main/java/io/b2mash/maestro/core/saga/SagaManager.java); [EnginePostgresParallelSagaIT.java:266-288](maestro-integration-tests/src/test/java/io/b2mash/maestro/integration/engine/EnginePostgresParallelSagaIT.java)). When two nodes race to append at the same slot, the loser **stands down and never adopts the winner's value**, marking its run sticky-stale so the next live activity throws even if workflow code swallowed the duplicate ([ActivityInvocationHandler.java:736-770](maestro-core/src/main/java/io/b2mash/maestro/core/engine/ActivityInvocationHandler.java)) — a strong choice that prevents a loser from recording a contradictory FAILED and running compensations.

The empirical evidence behind these claims is unusual for a pre-1.0 project: about **1,300 tests across 18 modules**, a 51-suite/147-test Testcontainers tier, a 10-scenario E2E on two lock backends, and a seeded 6-node chaos harness with store-level invariant checks ([test-plan.md:3, 71-104](docs/test-plan.md); [branch-verification.md:4-30](docs/superpowers/plans/2026-10-24-bugfix-cycle/triage/branch-verification.md)). Both PR #35 fixes spot-checked by the engine note — the saga anchor after a failed parallel and the 999-step branch cap — are in `main` with pinning tests ([DefaultWorkflowOperations.java:711-716, 841-842](maestro-core/src/main/java/io/b2mash/maestro/core/engine/DefaultWorkflowOperations.java); [WorkflowContext.java:349-356](maestro-core/src/main/java/io/b2mash/maestro/core/context/WorkflowContext.java)). The caveat is statistical, and here the third coordinator premise needed correcting: the weekly soak on pre-fix `main` was not continuously red. The live run history shows fail/fail/pass/fail/pass/pass/fail/pass/fail from 2026-08-09 to 10-04 and a pass on 11-01 on pre-fix code — **5 failures in 10 weekly runs** — which means two project docs that say "soak failed 5/5" and "not green since 2026-08-02" are contradicted by the run log ([test-plan.md:132-133](docs/test-plan.md); [multi-instance-test-plan.md:22-23](docs/multi-instance-test-plan.md); runs [31288365087](https://github.com/rakheen-dama/maestro/actions/runs/31288365087) through [41259326151](https://github.com/rakheen-dama/maestro/actions/runs/41259326151)). Because pre-fix code passed half the time, one green dispatched soak ([40762898010](https://github.com/rakheen-dama/maestro/actions/runs/40762898010), 2,320 workflows) plus one local soak is weak evidence that the intermittent I1 "wrongly FAILED under outage" class is closed, and **no scheduled E2E or chaos run had yet executed on the merged `c01d498`** as of 2026-11-03T23:25Z. The chaos evidence is strongest exactly where it matters most — I3 (no duplicate `(instance, seq)`) was clean everywhere — and weakest on I1.

## Four structural gaps decide which workloads it can carry

The first gap is the at-least-once contract. The live path runs the activity and *then* appends `ACTIVITY_COMPLETED`; nothing durable marks "started", so a crash anywhere between the external call returning and the append committing re-executes the activity on recovery ([ActivityInvocationHandler.java:514-559](maestro-core/src/main/java/io/b2mash/maestro/core/engine/ActivityInvocationHandler.java)). That is the standard durable-execution trade-off and the class Javadoc states it precisely: the unique index is "the primary idempotency guard: at most one outcome is ever persisted per sequence" and "the distributed lock is an optimization ... not a correctness requirement" ([ActivityInvocationHandler.java:58-63, 97-100](maestro-core/src/main/java/io/b2mash/maestro/core/engine/ActivityInvocationHandler.java)). But there is **no fencing token**: a lost lock renewal logs ERROR and drops the handle while the run carries on ([WorkflowInstanceLockManager.java:34-36](maestro-core/src/main/java/io/b2mash/maestro/core/engine/WorkflowInstanceLockManager.java)), lock-backend loss degrades to unlocked execution ([WorkflowInstanceLockManager.java:168-172](maestro-core/src/main/java/io/b2mash/maestro/core/engine/WorkflowInstanceLockManager.java)), and the measured "0 duplicate side effects across 2,587 workflows" is explicitly "not proven" ([operations.md:236-238](docs/operations.md); [open-issues.md:823-870](docs/open-issues.md)). There is also no transaction participation of any kind — no `DataSourceUtils`, `TransactionTemplate` or `@Transactional` outside `maestro-admin` — so an activity that writes to the same Postgres cannot be atomic with its own memo; DBOS-style `@TransactionalStep` is not on offer ([AbstractJdbcWorkflowStore.java:180, 236, 425](maestro-store-jdbc/src/main/java/io/b2mash/maestro/store/jdbc/AbstractJdbcWorkflowStore.java), per the red-team note). The problem this *creates* is documentary: the README still says "**No lost state. No duplicate side effects.**" ([README.md:34, 193](README.md)) while `operations.md` and the architecture doc say the opposite, and the author-facing `concepts.md` contains no occurrence of "at-least-once", "exactly-once" or "idempotent" at all — so the one place a workflow author looks never tells them their activities and compensations must be idempotent.

The second gap is silent: **activity arguments are never persisted**. The event row carries `(seq, type, stepName, payload)` where payload is the result ([WorkflowEvent.java:33-41](maestro-core/src/main/java/io/b2mash/maestro/core/model/WorkflowEvent.java)), and `stepName` is just `activityName + "." + method` ([ActivityInvocationHandler.java:333](maestro-core/src/main/java/io/b2mash/maestro/core/engine/ActivityInvocationHandler.java)). The drift guard therefore catches *which* operation ran at a slot but not *with what*. The red-team note's realistic scenario is a workflow iterating a `HashMap` of line items and calling `inventory.reserve(item)` per entry: the step names are identical at every slot, so after a JVM restart with a different iteration order the engine returns item A's stored reservation for item B's call and nothing can detect it. Overloaded methods on one activity interface share a step name for the same reason (an inference from the formula, not a documented limitation). The project knows the gap — `DeterminismChecker`'s Javadoc says the guard "still cannot detect ... a nondeterministic *value* that happens to produce the same step sequence" and warns to "treat a pass as evidence, not proof" ([DeterminismChecker.java:20-37](maestro-test/src/main/java/io/b2mash/maestro/test/DeterminismChecker.java)) — but the checker lives only in `maestro-test`, compares `sequence:eventType:stepName` fingerprints over 3 runs, and is not mentioned in `docs/testing.md` or `docs/getting-started.md`. Temporal records activity inputs in `ActivityTaskScheduled`; Maestro records only outputs, and the docs' Do/Don't table lists eight forbidden things while omitting `HashMap` iteration order, `System.getenv`, feature flags, `Locale.getDefault()`, `ZoneId.systemDefault()` and config refresh ([concepts.md:185-198](docs/concepts.md)).

The third gap is the sequence-space shape limit, and here the evidence corrects a loose premise: a *single* two-branch fork overflows only when the parent sequence exceeds about 2,147,480, not about 2,147, because `nextParentSeq = p*1000 + (n+1)*1000` is computed in `long` and guarded ([SequenceSpace.java:37-74](maestro-core/src/main/java/io/b2mash/maestro/core/engine/SequenceSpace.java)). The practical bound is compounding: a fork at seq 3 rebases the parent to about 7,000; a second fork to about 7,004,000; a third parent-line level — or compensation anchored after the second fork — needs about 7×10⁹ and overflows. The consequence documented in the project's own concepts doc is that **"a saga that has already made two sequential `parallel()` calls cannot compensate at all"**: the workflow ends FAILED with an ERROR listing steps to compensate by hand (Issue 28, open by design) ([concepts.md:466-477](docs/concepts.md); [open-issues.md:2504-2530](docs/open-issues.md)). Inside a branch the 999-slot cap bites ordinary loops: a `sleep` costs two slots and `retryUntil` costs `currentTime` plus the activity plus a sleep per attempt, so an hourly poll inside a `parallel()` branch fails the whole workflow after roughly 333 iterations (about 14 days), with nothing at authoring time to warn ([concepts.md:461, 481-503](docs/concepts.md)). The engine note also found that after a nested `parallel()` a branch's counter is rebased far beyond its original block, so the 999 bound check can no longer fire for the rest of that branch — a lost safety check rather than a collision risk, and not pinned by any test. There is no continue-as-new, snapshot, compaction or archival anywhere (repo-wide grep finds only the signal janitor), so a multi-year workflow's history and replay cost grow forever and every code change over its life must be gated with `version()` or it wedges ([00-spec-independent-assessment.md:70](docs/superpowers/plans/2026-10-24-bugfix-cycle/00-spec-independent-assessment.md)).

The fourth gap is in the signal model. `SignalMessage` is `(workflowId, signalName, payload)` with no id ([SignalMessage.java:19-23](maestro-core/src/main/java/io/b2mash/maestro/core/spi/SignalMessage.java)), so Kafka redelivery or a client retry persists twin rows; the chaos `InvariantChecker` reports byte-identical unconsumed twins as a finding rather than a violation, and Issue 32's fix for Valkey-pause-induced duplicates explicitly left the general "no idempotency key on `signal()`" problem open as "a larger API decision" ([InvariantChecker.java:74-79](maestro-integration-tests/src/test/java/io/b2mash/maestro/integration/e2e/chaos/InvariantChecker.java); [open-issues.md:2701-2779](docs/open-issues.md)). A narrower window is unpinned: consumption appends `SIGNAL_RECEIVED` *then* runs the `consumed=true` CAS, so a crash between the two leaves a signal consumed-by-log but `consumed=false`, and a later `awaitSignal` of the same name at a different sequence consumes it again ([SignalManager.java:1081-1118](maestro-core/src/main/java/io/b2mash/maestro/core/engine/SignalManager.java)). The engine chose this order because the reverse would *lose* the signal, which is the right trade, but workflows with repeated same-name awaits (`collectSignals`, loops) are exposed and no test pins it. Orphan rows for workflow IDs that never start are never purged because the janitor's subquery joins on `workflow_instance_id`.

A fifth problem cuts across all four: serialization. Payloads are written through the host application's shared `ObjectMapper` with no type information and no versioning envelope, and results are deserialized by the *current* method's generic return type ([PayloadSerializer.java:47-57, 92-103](maestro-core/src/main/java/io/b2mash/maestro/core/engine/PayloadSerializer.java); [ActivityInvocationHandler.java:419-425](maestro-core/src/main/java/io/b2mash/maestro/core/engine/ActivityInvocationHandler.java)). A replay-path `SerializationException` becomes an `UNKNOWN_EVENT_PAYLOAD` stand-down, not a failure ([UnknownHistoryGuard.java:107-119](maestro-core/src/main/java/io/b2mash/maestro/core/engine/UnknownHistoryGuard.java)). Both the engine and red-team notes reason from Jackson 3's default of ignoring unknown properties (neither verified it in-repo) that renaming a field without `@JsonAlias` reads as a silent null rather than a stand-down — the worse outcome — while removing an enum constant zombies the run. And because the mapper is the application's, an unrelated team changing `spring.jackson.*` for the web layer rewrites how durable history is read; the engine should own a private, frozen mapper and does not.

## Operations is where a first adopter will bleed

The single most consequential operational finding is that **nothing ever deletes completed workflow data**. The PRD specifies `archival: retention: 90d, strategy: delete` ([maestro-prd.md:426-428](docs/maestro-prd.md)); the property exists nowhere in code, and the project's own internal assessment says so ([00-spec-independent-assessment.md:70](docs/superpowers/plans/2026-10-24-bugfix-cycle/00-spec-independent-assessment.md)). The only automatic purge is the signal janitor, which removes *unconsumed* signals of COMPLETED/TERMINATED instances older than 7 days ([AbstractJdbcWorkflowStore.java:740-750](maestro-store-jdbc/src/main/java/io/b2mash/maestro/store/jdbc/AbstractJdbcWorkflowStore.java)). `PostgresMessageCleaner` and `PostgresLockCleaner` are registered as beans whose own Javadoc says the application must schedule them, and no main code does ([PostgresMessageCleaner.java:32](maestro-messaging-postgres/src/main/java/io/b2mash/maestro/messaging/postgres/PostgresMessageCleaner.java); [PostgresLockCleaner.java:22](maestro-lock-postgres/src/main/java/io/b2mash/maestro/lock/postgres/PostgresLockCleaner.java)). The admin dashboard's `admin_event` table has no DELETE anywhere. Growth is unbounded in six places, there is no index on `completed_at`, `service_name` or `workflow_type`, FKs have no `ON DELETE CASCADE`, and the docs contain no guidance on vacuum, partitioning, pool sizing or archiving ([V1__create_maestro_schema.sql:9-54](maestro-store-postgres/src/main/resources/db/maestro/store/V1__create_maestro_schema.sql); [V2__create_indexes.sql:5-30](maestro-store-postgres/src/main/resources/db/maestro/store/V2__create_indexes.sql)). The red-team note's framing is apt: the event log is a replay cache full of customer-data JSONB (the `UnknownHistoryGuard` redacts messages for exactly that reason, [UnknownHistoryGuard.java:124-131](maestro-core/src/main/java/io/b2mash/maestro/core/engine/UnknownHistoryGuard.java)) that the team did not design, now inside their backups and PITR window, with a GDPR-erasure path they must write themselves in FK order.

All of this runs on the host application's own `DataSource`, injected by type with no qualifier and no property for a separate pool or schema ([PostgresStoreAutoConfiguration.java:94, 121-126](maestro-store-postgres/src/main/java/io/b2mash/maestro/store/postgres/PostgresStoreAutoConfiguration.java)). The hot path is lean — one memo SELECT and one autocommit INSERT per live activity, no instance UPDATE ([ActivityInvocationHandler.java:322-576](maestro-core/src/main/java/io/b2mash/maestro/core/engine/ActivityInvocationHandler.java)) — but the background load is the problem. Recovery is an **unfiltered full scan of every active instance by every node every 60 s**, no `LIMIT`, no service filter, loading JSONB input/output for every row, followed by a lock probe per row ([AbstractJdbcWorkflowStore.java:221-229](maestro-store-jdbc/src/main/java/io/b2mash/maestro/store/jdbc/AbstractJdbcWorkflowStore.java)); Issue 12 measured the query rate linear in node count and is "open by design" ([open-issues.md:989-1110](docs/open-issues.md)). Admission is gated only by the instance lock, not by task-queue capacity, so one node can hoard a queue's whole backlog while peers idle (Issue 30), and lock renewal is a single thread iterating held locks serially against a 30 s TTL ([WorkflowExecutor.java:1767-1793](maestro-core/src/main/java/io/b2mash/maestro/core/engine/WorkflowExecutor.java); [WorkflowInstanceLockManager.java:260-281](maestro-core/src/main/java/io/b2mash/maestro/core/engine/WorkflowInstanceLockManager.java)). The engine note's inference ties these together: a fleet restart with thousands of active instances is the regime where serial renewal approaches TTL, locks are lost, and the no-fencing window of Issue 11 opens — and nothing in the repo measures it; the benchmark of record is at ≤10 parked instances and the internal estimate is "10k parked on one node ≈ 1.7k ops/s idle" ([00-spec-independent-assessment.md:73](docs/superpowers/plans/2026-10-24-bugfix-cycle/00-spec-independent-assessment.md)). The Backend Comparison table's "~5-10k msg/s" and "sub-ms locks" cite no benchmark and should be treated as marketing ([configuration.md:372-381](docs/configuration.md)); `test-plan.md` lists performance testing as out of scope.

The stand-down design is a sound safety net that converts corruption into wedging, but it imposes an operational tax the docs state and the dashboard hides. Three kinds exist — `unknown_event_type` heals when an upgraded node adopts; `unknown_event_payload` and `nondeterministic_history` do not — and on a homogeneous fleet the payload case is a "**silent zombie — the workflow never completes, never fails, and re-adopts forever**" ([operations.md:490-569, 639-747](docs/operations.md)). Churn is by design: every 60 s recovery pass re-adopts, replays the full history one SELECT per step, stands down, and emits one WARN plus one counter increment ([operations.md:717-720](docs/operations.md)). The only signal is `maestro.standdown{reason}`; the dashboard surfaces no stand-downs, dead letters or lock state. The deploy rule is "**upgrade every node of a service together, or drain the service first**", there is no drain API or CLI, and the current release's two-slot `awaitSignal` layout means **rollback requires rolling forward** ([operations.md:426-450](docs/operations.md)). Every milestone so far (0.3.0, 0.4.0, Unreleased) has added event types or a non-rolling migration, so adopters should expect pre-1.0 upgrades to be downtime events ([release-notes.md:42-58, 658-679, 1280-1285](docs/release-notes.md)); §10 of the operations doc "carries no measured numbers" and mixed-version behaviour is tested only by editing history in SQL, never on a real two-version cluster.

Admin Retry is an operator action that can corrupt a run. It deletes every `ACTIVITY_FAILED` memo including ones the workflow *caught and branched on*, so if the retried activity now succeeds the run stands down as `nondeterministic_history` with no code-level remedy — the doc's advice is "avoid admin Retry on workflows that catch activity failures and branch on them" ([operations.md:709-741](docs/operations.md)). Open Issue 33 compounds it: retry attributes the failure to the highest-sequenced `SIGNAL_TIMEOUT`, which can be a caught gate because branch slots sort above later main-line slots, and since R61 it then deletes the wrong await's memo and timer ([open-issues.md:2783-2823](docs/open-issues.md)). The operations note's ranking — Retry is unsafe for any workflow that catches `SignalTimeoutException` or `ActivityExecutionException` and branches — is the right reading.

Kafka and the dashboard both carry claims the code does not back. "Maestro never auto-creates Kafka topics" is policy, not code: the consumer factory never sets `allow.auto.create.topics`, there is no `missingTopicsFatal`, and auto-create is prevented only broker-side in `docker-compose.yml:73`; a missing topic makes `startWorkflow` block for 60 s per start, which was the never-explained 6/6 loan E2E failure (Issue 3) ([KafkaMessagingAutoConfiguration.java:186-208](maestro-messaging-kafka/src/main/java/io/b2mash/maestro/messaging/kafka/config/KafkaMessagingAutoConfiguration.java); [open-issues.md:2880-2895](docs/open-issues.md)). Container concurrency is left at Spring's default of 1, a retrying record blocks its whole topic on that node, and a missing `.DLT` stalls consumption after a WARN-only startup probe ([KafkaRedeliveryErrorHandlers.java:21-82](maestro-messaging-kafka/src/main/java/io/b2mash/maestro/messaging/kafka/KafkaRedeliveryErrorHandlers.java); [KafkaDeadLetterTopicCheck.java:139-141](maestro-messaging-kafka/src/main/java/io/b2mash/maestro/messaging/kafka/KafkaDeadLetterTopicCheck.java)). The admin dashboard is a separate deployable with its own Postgres, Kafka-only ingestion, "no authentication, authorization, or provenance check" ([admin.md:306-314](docs/admin.md)), and **every engine lifecycle publish passes `detail = null`** ([WorkflowExecutor.java:2647](maestro-core/src/main/java/io/b2mash/maestro/core/engine/WorkflowExecutor.java); [ActivityInvocationHandler.java:892](maestro-core/src/main/java/io/b2mash/maestro/core/engine/ActivityInvocationHandler.java)), so no step input, output or error is ever visible; `docs/admin.md:151-169` instructs adding `maestro-admin-client`, whose `AdminEventPublisher` has no production caller. Observability covers version skew and lock loss well (11 counters, 1 timer, 2 node-local gauges, real spans and W3C propagation) but has no stuck/aging-workflow metric, no recovery-backlog gauge, no DLT or leadership meter, and `runAbandoned` for `NODE_ERROR`/`TERMINAL_WRITE_FAILED` is deliberately log-only — so the two "page now" conditions in `operations.md §10.9` are not alertable from metrics, and the health indicator ignores the lock backend entirely, keeping a Kubernetes readiness probe UP while a node runs every workflow unlocked ([observability.md:68-181](docs/observability.md); [MaestroHealthIndicator.java:70-186](maestro-spring-boot-starter/src/main/java/io/b2mash/maestro/spring/health/MaestroHealthIndicator.java)).

The Postgres-only topology, which the README positions as the low-friction entry point, is the least covered: its transport has a hardcoded 1 s claim poll, pins one pooled connection for the process lifetime for `LISTEN` (incompatible with PgBouncer transaction pooling), opens one channel per parked workflow, can spawn up to 1,000 concurrent `NOTIFY` connection borrows per node against a default Hikari pool of 10, loses the dashboard and the `@MaestroSignalListener` bridge, and has **no multi-node E2E or chaos coverage** — the E2E "two backends" matrix is Valkey-lock vs Postgres-lock on a Kafka transport ([PostgresWorkflowMessaging.java:117, 232-288](maestro-messaging-postgres/src/main/java/io/b2mash/maestro/messaging/postgres/PostgresWorkflowMessaging.java); [PostgresNotificationListener.java:84-89](maestro-messaging-postgres/src/main/java/io/b2mash/maestro/messaging/postgres/PostgresNotificationListener.java); [operations.md:286-302](docs/operations.md)).

## Day one is easy; day thirty teaches the idioms

The adoption path is genuinely small: five Gradle coordinates plus `spring-boot-starter-jdbc`, one required property (`maestro.service-name`, enforced with an `IllegalStateException`), four annotations and one injected `MaestroClient` with three methods ([README.md:52-63](README.md); [MaestroAutoConfiguration.java:85-87](maestro-spring-boot-starter/src/main/java/io/b2mash/maestro/spring/config/MaestroAutoConfiguration.java); [MaestroClient.java:71-100](maestro-spring-boot-starter/src/main/java/io/b2mash/maestro/spring/client/MaestroClient.java)). There is no worker-registration step — workflow classes are classpath-scanned into prototype beans — which is a real simplification over Temporal's SDK. Every annotation carries a usage example and a constraints list in its Javadoc, the 40-property `maestro.*` namespace is constructor-bound records with generated IDE metadata, removed properties fail startup rather than being silently ignored, and the documentation runs to about **12,100 lines across 17 files** including a 2,895-line open-issues register that reads like an engineering log ([configuration.md](docs/configuration.md); [open-issues.md](docs/open-issues.md)). The DX note's code-volume analysis puts the order workflow at 97 lines (about 50 of body) inside a 465-line sample, and estimates (as opinion) that a plain-Spring equivalent would need 400-800 additional lines of state table, timeout scheduler, correlation consumer, idempotency bookkeeping and recovery code, plus the concurrency bugs those entail — the engine's own register documents 26 resolved library defects of exactly that class.

The flagship sample undermines the pitch. `@Saga` compensation fires only when the workflow method *throws*: `failAndCompensate` is called only from the executor's catch arms, a normal return goes to COMPLETED, and `EnginePostgresSagaIT:161` pins that a successful saga must not compensate ([WorkflowExecutor.java:1931-1932, 2051-2053](maestro-core/src/main/java/io/b2mash/maestro/core/engine/WorkflowExecutor.java)). Yet `OrderFulfilmentWorkflow` handles `SignalTimeoutException` with `return OrderResult.failed("Payment timed out"); // @Saga compensation: inventory.releaseReservation() runs automatically` — the comment sits after the `return` — and the `!paymentResult.success()` branch also returns normally ([OrderFulfilmentWorkflow.java:64-76](maestro-samples/sample-order-service/src/main/java/io/b2mash/maestro/samples/order/workflow/OrderFulfilmentWorkflow.java)). The samples README promises that `DECLINE_ME` "triggers automatic inventory release" ([maestro-samples/README.md:124, 174](maestro-samples/README.md)), the sample's test has no failure-path case, and the testing guide's "Full Test Example" asserts `releaseReservation` after a failed payment while using record shapes, an activity interface and a `status()` accessor that do not exist in the sample it names ([testing.md:392-460](docs/testing.md)). The DX note did not execute the demo, but the verified chain means the shipped `DECLINE_ME` scenario most likely completes `COMPLETED` with `success=false` and never releases the reservation. This matters out of proportion to its size: "return a failed result" versus "throw" is precisely where saga frameworks diverge, the concepts doc never states the rule, and a developer copying the flagship sample inherits the bug.

Beyond that, the author must internalise a set of Maestro idioms the Javadoc documents but the tutorial does not teach: `causedBy(Class)` instead of `catch (MyDomainException)`; `volatile` on fields read by `@QueryMethod` and the fact that `query()` works only on the owning node — both sample controllers call it bare with no `WorkflowNotQueryableException` fallback ([OrderController.java:49-53](maestro-samples/sample-order-service/src/main/java/io/b2mash/maestro/samples/order/controller/OrderController.java); [DocumentController.java:59-63](maestro-samples/sample-postgres-only/src/main/java/io/b2mash/maestro/samples/document/controller/DocumentController.java)); the `@RetryPolicy` all-defaults rule under which customising one attribute silently opts out of every `maestro.retry.*` property ([RetryPolicy.java:25-36](maestro-core/src/main/java/io/b2mash/maestro/core/annotation/RetryPolicy.java)); two-slot awaits and the 999-slot budget; and the fact that `DuplicateEventException` and `StaleRunException` are ordinary exceptions a broad catch *can* swallow, with a second charge or email as the documented consequence ([concepts.md:163-175](docs/concepts.md)). `WorkflowOptions` has exactly one field, `workflowId` — no workflow timeout, no ID-reuse policy, no start delay — and there is no client `cancel`, no list/search, no `getHistory`, no heartbeat API, no cron/schedules and no child workflows ([WorkflowOptions.java:17-19](maestro-spring-boot-starter/src/main/java/io/b2mash/maestro/spring/client/WorkflowOptions.java)). The getting-started tutorial also still says `startAsync` "enqueues execution on Kafka" when the run starts in-process on a virtual thread ([getting-started.md:327](docs/getting-started.md); [WorkflowExecutor.java:1840](maestro-core/src/main/java/io/b2mash/maestro/core/engine/WorkflowExecutor.java)), and internal tracker IDs (R59, F1, Issue 26) leak into user-facing prose.

The test kit is where two notes most visibly disagree, and both are right at different layers. The DX note calls `maestro-test` "the best-developed part of the developer experience": the production `WorkflowExecutor` on in-memory SPIs that emulate the unique index, CAS and optimistic locking; a controllable clock whose `advanceTime(timeout)` lands exactly on durable deadlines; pre-delivered signals; event-log inspection; a JUnit extension ([TestWorkflowEnvironment.java:108-312](maestro-test/src/main/java/io/b2mash/maestro/test/TestWorkflowEnvironment.java)). The red-team note calls it "green unit tests, red production" because **the kit never replays**: activity results are deserialized only on the replay path, there is no crash/recover/replay helper, the executor is not exposed, lock TTL runs on wall clock not the test clock, and the kit wires workflows differently from the starter (no-arg constructor via reflection, `getDeclaredMethods` versus `getMethods`), so a standard unit suite exercises zero deserialization and zero recovery ([ActivityInvocationHandler.java:360, 371-374](maestro-core/src/main/java/io/b2mash/maestro/core/engine/ActivityInvocationHandler.java); [InMemoryDistributedLock.java:29-70](maestro-test/src/main/java/io/b2mash/maestro/test/InMemoryDistributedLock.java)). The project's own loan sample gets recovery coverage only by hand-building a `WorkflowExecutor`, calling `recoverWorkflows` and loading a "v2" class through a child-first `URLClassLoader` — undocumented internal API — and the multi-node `MaestroEngineHarness` is not published ([LoanApplicationWorkflowV2Test.java:121-131, 365, 560](maestro-samples/sample-loan-origination/loan-application-service/src/test/java/io/b2mash/maestro/samples/loan/application/workflow/LoanApplicationWorkflowV2Test.java)). The synthesis: the ergonomics are excellent and the fidelity gap sits exactly over the two bug classes most likely to reach production — serialization-on-replay and value-level nondeterminism — and a `crashAndRecover()` on the test handle would close most of it. Smaller ergonomic debts: the "wait until parked, then advance time" dance is reinvented three ways (tutorial `Thread.sleep` loop, docs helper that does not compile, samples with Awaitility), and a failed workflow surfaces in tests as a bare `RuntimeException` wrapping raw JSON rather than the typed `WorkflowExecutionException` the production client throws ([TestWorkflowHandle.java:83-110](maestro-test/src/main/java/io/b2mash/maestro/test/TestWorkflowHandle.java)).

The platform floor is the hardest barrier. Maestro hard-requires **Java 25** (the toolchain and `ScopedValue` binding the workflow context), Spring Boot 4.0.x pinned in three convention plugins, Jackson 3 `tools.jackson`, Flyway 11 as a hard transitive dependency even in `schema.mode=none`, and `maestro-test` puts **JUnit 6.0.1** on every consumer's test classpath while `docs/testing.md:36` says JUnit 5 ([maestro.java-conventions.gradle.kts:9-20](build-logic/src/main/kotlin/maestro.java-conventions.gradle.kts); [WorkflowContext.java:10, 33-34](maestro-core/src/main/java/io/b2mash/maestro/core/context/WorkflowContext.java); [maestro-test/build.gradle.kts:7-10](maestro-test/build.gradle.kts)). Spring Boot 4 itself runs on Java 17, so the Java 25 floor excludes every Boot 4 shop still on 17 or 21. And nothing is on Maven Central: "adoption" today is `publishToMavenLocal` from source, the BOM's POM points at a non-existent `github.com/maestro-workflow/maestro`, and the tree carries stale `.flattened-pom.xml` artefacts and an orphan `sample-rabbitmq-order-service/` directory with no sources ([README.md:66](README.md); [maestro-bom/build.gradle.kts:31-49](maestro-bom/build.gradle.kts)).

## A unique bundle in a quadrant DBOS already occupies

Every architectural slot Maestro claims is already taken by a shipping product. The "embedded, no server, Postgres as truth, code-first Java" quadrant belongs to **DBOS Transact Java, which reached 1.0 on 2026-07-01** with a Spring Boot starter, `@TransactionalStep`, durable queues with rate limits and dedup, `@Scheduled` cron, send/recv, patching plus application-version-scoped recovery, and a paid Conductor UI from $99/month ([DBOS Java README](https://github.com/dbos-inc/dbos-transact-java); [Upgrading workflows](https://docs.dbos.dev/java/tutorials/upgrading-workflows); [DBOS pricing](https://www.dbos.dev/pricing)). Temporal — $12.55B valuation after a $550M Series E, more than 43 million open-source installations in August 2026 and 4,300+ paying customers — ships a Spring Boot 2/3/4 starter with Actuator metrics, OpenTelemetry and an in-memory test server, and has Worker Versioning in GA ([Pulse 2.0](https://pulse2.com/temporal-raises-550-million-series-e-at-12-55-billion-valuation/); [Temporal Spring Boot integration](https://docs.temporal.io/develop/java/integrations/spring-boot-integration)). Restate raised a $20M Series A in October 2026 behind a BSL server and MIT Spring Boot SDK ([Pulse 2.0](https://pulse2.com/restate-raises-20-million-series-a-led-by-singular/)), and AWS shipped a GA Lambda Durable Execution SDK for Java in April 2026 ([AWS What's New](https://aws.amazon.com/about-aws/whats-new/2026/04/lambda-durable-execution-java-ga/)). Against that, Maestro has 1 star, 0 forks, 1 contributor, 0 releases and no published artefacts (GitHub API, 2026-11-04).

Taken one at a time, none of Maestro's differentiators is unique. What is unique is the bundle for one audience: Spring Boot 4 / Java 25 / virtual threads as the primary baseline; declarative `@Saga`/`@Compensate` (Temporal offers a `Saga` helper class, DBOS Java none); `@MaestroSignalListener` Kafka-topic-to-signal routing with W3C trace propagation (no built-in equivalent in DBOS Java, whose Show HN critique was precisely that every example is single-app/single-DB); and an Apache-2.0 dashboard where DBOS charges and Restate and Camunda restrict production use ([DBOS Show HN](https://hn.svelte.dev/item/45920156); [Camunda licences](https://docs.camunda.io/docs/reference/licenses/)). Each is a feature a funded competitor could add in a release cycle; none is a structural moat. The Boot 4 baseline is a *transient* advantage — DBOS pins Boot 3.5 "for LTS" with Boot 4 test-only today, and with Boot 3.5 out of OSS support since 30 June 2026 that will flip within months ([DBOS libs.versions.toml](https://github.com/dbos-inc/dbos-transact-java/blob/main/gradle/libs.versions.toml); [HeroDevs](https://www.herodevs.com/blog-posts/spring-boot-versions-eol-dates-and-latest-releases-april-2026)).

The demand signal is real but skews away from the JVM. The Absurd and pg_durable HN threads drew 474 and 359 points for "Temporal without the server" and the DBOS Postgres post 359, but DBOS Java has **248 stars after 17 months against 1,665 for its Python sibling**, and its Show HN drew 113 points ([HN 48414367](https://news.ycombinator.com/item?id=48414367); [HN 48313530](https://news.ycombinator.com/item?id=48313530)). Surveys put Java 17 and 21 at roughly 70-85% of use combined; the only Java 25 share found (~10%) is unsourced, and the only Spring Boot telemetry (HeroDevs, laggard-skewed) gives no 4.x figure at all, which itself suggests a small minority as of April 2026 ([InfoWorld/Azul 2025](https://www.infoworld.com/article/2335141/java-11-and-java-17-lead-java-usage-azul-survey-finds.html); [JetBrains 2025](https://lp.jetbrains.com/the-state-of-java-2025); [HeroDevs 3.5 EOL](https://www.herodevs.com/blog-posts/spring-boot-3-5-eol-what-the-migration-really-takes)). The 2026 funding narrative is "AI agents that crash"; Maestro's PRD and README tell an e-commerce-saga and loan-origination story, which is a sound enterprise-Java pitch but out of step with where attention is. The competitive note's reading of the 1.0 bar the market implies — published semver artefacts with a migration policy, version-scoped recovery, child workflows, cron, continue-as-new or compaction, queryable attributes, a replayer, a durable retry counter, and a second maintainer or governance statement — is a fair list; the PRD's own non-goal of "full workflow versioning / migration tooling" is a notable admission for a replay-based engine.

Project risk compounds this. All **584 commits are by one author**, about 85% carry an AI co-author trailer, the process artefacts (`.superpowers/sdd/`, 125 files) are committed, and `tasks/lessons.md:70` records that "evidence fabrication recurred three times before the rule was made mechanical" ([tasks/lessons.md:70](tasks/lessons.md)). `main` has no branch protection and PRs #30 and #31 merged red; the nightly schedule was silently auto-disabled by GitHub from 2026-10-10 to 10-28 and now needs a keepalive job; `release.yml` and `javadoc.yml` have never run; `gradle.properties` says `0.3.0-SNAPSHOT` while the release notes describe 0.4.0 ([.github/workflows/build-test.yml:47-58](.github/workflows/build-test.yml); [gradle.properties:1-2](gradle.properties)). The repo's own pre-fix-cycle self-assessment scored correctness 5/10 and operations 4/10 ([00-spec-independent-assessment.md:122](docs/superpowers/plans/2026-10-24-bugfix-cycle/00-spec-independent-assessment.md)); PR #35 moved correctness up materially and operations barely at all. The red-team note's deeper point stands: the 17.5k-line core's invariants (two-slot awaits, ×1000 partitioning, three `Error` control-flow types, three stand-down kinds) are documented at length precisely because they are intricate, and no second human has internalised them.

## Where the five notes disagree, and how the evidence weighs

On the chaos soak, the engine-correctness note (relaying a delegated reader) says the soak "was red for two months before the schedule was silently disabled", echoing `test-plan.md`'s "failed 5/5". The operations note pulled the live run log with run IDs and found passes on 08-23, 09-06, 09-13, 09-27 and 11-01. The run log wins: the soak was intermittent, which is *worse* evidence for the fix (a 50% pass rate on broken code means one green run proves little) but a more accurate picture of the harness.

On the admin dashboard, the DX note — which read `docs/admin.md` only and said so — describes a useful timeline "with expandable JSON"; the operations and red-team notes read the code and found every lifecycle publish passes `detail = null`, so no payload or error is ever shown. The code read wins; the dashboard is a liability at this stage, not an asset, and the DX note's inference that Postgres-only developers "have only logs" applies to Kafka developers too in practice.

On the test kit, the DX and red-team notes reach opposite verdicts from the same facts. Both are correct about different things: ergonomics are strong, fidelity on the replay path is absent. The report scores the kit as a strength with a specific, closable gap rather than averaging the two.

On the sequence-depth ceiling, the engine note corrects the brief's arithmetic (a single fork overflows at a parent seq above ~2,147,480, not ~2,147) while the red-team note frames the compounding bound as the practical limit. These agree once the arithmetic is fixed; the compounding bound and Issue 28 are what matter to authors.

On Jackson's handling of removed or renamed fields, both the engine and red-team notes reason from Jackson 3 defaults and both flag that they did not verify it in-repo. The report carries the inference as an inference.

## What would change the verdict

Upward, cheaply and before a first release: fix the order sample to throw on timeout and decline, add a failure-path test, and rewrite the testing-guide example against the real types — this alone converts the first evaluator's experience from "the saga demo is wrong" to "the saga demo works". State the at-least-once contract and the idempotency requirement for activities and compensations in `concepts.md`, and remove the README's "No duplicate side effects". Correct the getting-started "enqueues on Kafka" sentence. Ship a documented retention runbook (purge SQL in FK order, a `completed_at` index) even if an engine-owned purger comes later, and schedule the two Postgres cleaners by default. Make a missing Kafka topic or DLT fail startup or `startWorkflow` loudly instead of hanging. Add a `crashAndRecover()` or replayer to `TestWorkflowEnvironment` and surface `DeterminismChecker` in `docs/testing.md`. Fix the two docs that misstate the soak history, and let several scheduled nightlies and at least two weekly soaks run on the merged commit before calling the I1 class closed. Those changes would move ease of use to 7-8 and operations to 5-6 without touching the engine.

Upward, structurally: a fencing token validated in the store on append (the Javadoc already names it as future work) would turn Issue 11 from a documented hazard into a guarantee; persisting activity arguments, or at least a hash of them, in the event row would let `ReplayGuard` catch value-level drift; an engine-owned frozen `ObjectMapper` would decouple durable history from the host's web JSON configuration; a stand-down backoff or quarantine status would stop zombies from replaying full histories every 60 s; and continue-as-new or history compaction would lift both the multi-year-workflow problem and the sequence-depth ceiling for looping sagas. Adding cron, child workflows and a durable retry counter closes the table-stakes gap with DBOS Java 1.x. Any of these moves correctness to 8 and value to 8.

The market score moves only with decisions outside the code. Publishing versioned artefacts to Maven Central with a stated compatibility policy is the precondition for anyone evaluating at all. Either relaxing the floor to Java 21 (if `ScopedValue` can be replaced with `ThreadLocal` plus explicit propagation, or isolated behind a multi-release jar) or writing down why Java 25 is mandatory and what it buys is the single largest lever on addressable market, because Boot 4 itself runs on 17. A second maintainer, a governance statement and branch protection address bus-factor-one. And the positioning should lean into the only story competitors do not tell — multi-service choreography over Kafka with sagas inside each service — rather than "Temporal-grade", a phrase the README has already dropped but `CLAUDE.md:5`, `concepts.md:11` and the PRD still carry.

Downward: the verdict would fall if the first nightlies on `c01d498` reproduce the I1 "wrongly FAILED under outage" class (the fix is one green run against a 50% historical pass rate), if the Postgres-only transport — the README's low-friction entry — turns out to have correctness defects when it finally gets multi-node chaos coverage, or if the HashMap-order silent-replay scenario is reproduced as a test and found to be common in real workflow code.

## Conclusion

The honest summary is that Maestro has solved the hard problem and left the easy ones undone. The replay engine, the control-flow error design, the two-slot park layouts, the saga anchoring and the stand-down philosophy are the work of someone who understood where durable-execution engines break and built guards at each break — and the chaos harness that proves it is a credibility asset most pre-1.0 projects do not have. But a first-release evaluator never reaches the engine; they reach the README's over-claim, a sample whose saga does not fire, a tutorial that describes a Kafka task channel that no longer exists, a Java 25 requirement their platform team will veto, and a `publishToMavenLocal` instruction. The gap between the engine's quality and the surface's quality is the project's defining feature at `c01d498`, and it is closable in weeks, not quarters, because almost none of it is engine work.

The deeper implication is about where to spend the next cycle. The 2026-10-24 bug-fix cycle lifted correctness from the self-assessed 5/10 to a defensible 7; the same effort applied to operations (retention, loud Kafka failures, a replayer in the test kit, a stand-down quarantine) and to the three sample/doc defects would lift the two lowest scores more than any further engine hardening could. The market position, though, will not move with code: DBOS Java 1.0 already owns the quadrant on JDK 17, and Maestro's remaining differentiation — sagas plus Kafka-signal choreography between Spring services — is a story only a published artefact, a relaxed or justified platform floor, and a second maintainer can make credible. Ship the pre-1.0 once the surface matches the engine; decide the Java 25 question before, not after.
