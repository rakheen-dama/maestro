Act I / the problem

A mortgage is not a request and a response.

It is the process from a borrower applying to money leaving the lender’s account — and it runs for days to weeks.

It outlives your deployment

A loan in flight will be redeployed to, restarted, and crashed into. The process has to survive all three without a human reconstructing it.

Nobody coordinates

Borrower and co-borrower act independently. Credit, employment and appraisal providers answer in any order, at any latency — and sometimes twice. A human underwriter may never answer at all.

It ends in money

A rate lock is reserved and funds are disbursed. Those two steps cost real money and are expensive to undo, so “just run it again” is not an available answer.

SAY: Loan origination is not a contrived example picked to flatter a workflow engine — it is the canonical shape of the problem workflow engines exist for. Long-running, uncoordinated parties, irreversible ending. Every awkward property of it maps onto something the engine has to get right.

DO: Nothing live. This is the framing before §1.

Act I / the flow / LoanApplicationWorkflow

Eight steps. Everything you see today happens inside them.

  1. 01Validate and record — the application becomes durable state.
  2. 02Fan out three verifications — credit, employment, appraisal.
  3. 03Fan in, in any order — one signal name, loop until all three types have arrived. Duplicates tolerated.
  4. 04Collect documents — from either borrower, in any order.
  5. 05Withdrawal gate #1 — nothing reserved yet, so withdrawing fails cleanly with no compensation.
  6. 06Underwriting, up to three rounds — approved, rejected, or conditions. Conditions means “more paperwork” and another round.
  7. 07The funding saga — reserve rate lock → collect signatures → disburse. Withdrawal gate #2 sits just before disbursement; compensation releases the lock.
  8. 08Complete — the loan is funded.

loan-application-service :8091 orchestrates  ·  verification-gateway-service :8092 plays the three providers  ·  underwriting-service :8093 holds the humans

SAY: Keep this shape in your head. The five scenarios are all the same eight steps under different pressure — a crash, a withdrawal, a deploy. Note step 5 and step 7: cancellation is honoured at defined points, and where the gate sits decides whether money has to be cleaned up. That is a business decision, made explicit in code.

Act II / scenario 2 / §2 / the pause

The silence is the engine deciding it is allowed to resume.

  1. 01The lock expires — the node that owned this workflow died holding it. Nobody can hand it over; nothing got the chance to release it.
  2. 02A recovery poll notices the workflow is unowned — the restarted process here, a surviving peer in a real cluster. Same mechanism either way.
  3. 03The workflow method is re-invoked from its first line — every completed activity returns its stored result out of Postgres. No HTTP call, no Kafka publish. Replay runs at memory speed.
  4. 04Real work resumes at the first step with no stored result — the resume itself is instantaneous.

How fast does it recover? Answer with the knob

“As fast as you configure it to notice.” The demo sets the recovery poll to 5 s so it is watchable; the shipped default is 60 s, and at that default this same phase measured 250 s.

The residual 33 s is Kafka’s, not Maestro’s

A kill -9 leaves the broker believing the dead consumer is still a live group member until session.timeout.ms (45 s) runs out. The restarted node cannot be assigned the decisions topic until the group rebalances. A clean restart rejoins in 3 s.

SAY (start the moment waiting for the rate lock appears — do not stand quietly through this, it reads as a hang): Watch what has to happen before that line appears. The node that owned this workflow died holding a lock, so first that lock has to expire — nobody can hand it over, because nothing got a chance to release it. Then a recovery poll has to notice the workflow is unowned and take it. Then the workflow method is re-invoked from the very first line, and every activity that already completed returns its stored result out of Postgres instantly. It runs the replay at memory speed until it reaches the first step with no stored result, and only then does real work happen again. Everything you are waiting for right now is the engine deciding it is allowed to resume — the resume itself is instantaneous.

SAY when the rate lock line lands: There it is. And the proof is on the next screen — the rows recorded before the kill are byte-identical.

DO: §2, during drive-loan.sh finish. Nothing to click: this slide is what you say while the terminal is quiet.

WATCH OUT: the honest answer if asked about the 33 s is that the recovery mechanism was ready long before the message bus was. Do not let it read as Maestro being slow, and do not quote a recovery number without the poll interval attached.

One argument you must not get wrong.

static final int PARALLEL_VERIFICATION_VERSION = 2;

        PARALLEL_VERIFICATION_VERSION);
// ... steps 1 and 2 are identical in both versions ...

            () -> { awaitAllVerifications();              return "verifications"; },

maestro-samples/sample-loan-origination/loan-application-service/src/v2/java/…/workflow/LoanApplicationWorkflow.java  ·  comments elided, lambda bodies folded onto one line

Never version(changeId, 1, 2)

DEFAULT_VERSION is -1. A history that predates the change resolves to it, so a literal 1 floor puts every in-flight loan below the minimum — throwing UnsupportedWorkflowVersionException, failing the loan and running its saga compensations. That is a recorded RED test, not a hypothetical.

Why the gate sits before step 1

version() peeks the next sequence slot without consuming it. Resolving here pins every loan that has already recorded its application. Resolve it later and a loan parked at the very first await would find an empty slot, record version 2, and switch paths mid-flight.

SAY: That is the entire change. A named change id — durable, never renamed — a minimum, a maximum, and a branch. The engine writes the resolved version into the event log as a VERSION_MARKER row the first time a workflow reaches this line, and from then on that loan is pinned. Old loans keep the old path forever; new loans get the new one. You delete the old branch when no pre-change loan can still be running.

SAY the second argument out loud: WorkflowContext.DEFAULT_VERSION, not 1. DEFAULT_VERSION is -1 and it means "this history predates the change". Writing the literal 1 as the minimum fails every in-flight loan — it inverts the entire point of the gate. Evidence: demo/.evidence/task-3-red-2-brief-literal-bounds-fail-inflight.log.

DO: §D1. No commands on this slide — it is the code behind what the script just proved.

IF ASKED why the branches return a String: parallel() collects results with List.copyOf, which rejects nulls, so a Callable<Void> branch fails the workflow with a message-less NPE. And both helpers call WorkflowContext.current() rather than closing over the parent context, because inside parallel() the current context is the branch context with its own partitioned sequence space.

On recovery, the method runs from the top

At each activity call the proxy asks Postgres: is there a row at this sequence number? If yes, it returns the stored result and the activity body never executes. If no, it executes, persists, returns.

There is no snapshot

No serialised continuation, no thread state on disk. This table is the whole of it. SIDE_EFFECT rows are workflow.currentTime() and workflow.randomUUID() — the non-deterministic bits, recorded once so replay sees the same values.

Two nodes cannot both win

idx_wf_event_replay is UNIQUE (workflow_instance_id, sequence_number). Racing nodes cannot both persist a result for the same step.
